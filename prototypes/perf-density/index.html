Making the probe readable

The 100-request performance probe lands 1–2 s requests next to audit requests that take up to three minutes. On one linear axis the probe flattens into a row of overlapping rings at zero. Below are four alternatives to the current chart. All of them use the same synthetic run, which is shaped like the reported screenshot. Hover, tap, or focus a chart and use the arrow keys to step through requests.

A · Current chart

reference

The production rendering: linear y in raw milliseconds, r=4 dots with a 2 px surface ring, and a running median over each endpoint's last 5 requests across both phases.

Problems

  • The probe's 0–2 s spread fits into about 2 px of height, so every probe request sits on the zero line.
  • The surface rings overlap into a chain, and you can't tell where one request ends and the next begins.
  • The median mixes audit and probe requests, so it holds at 100 s and then drops straight down.
  • Hover only works by landing on a 9 px dot, which fails on touch and with tremor.
Option 1

B · Log scale

smallest change

Same chart and marks, with a log₁₀ y-axis labelled in human units (100 ms, 1 s, 10 s, 100 s). The probe's spread gets visible height.

Gains

  • About a 20-line change in chartSvg(), and every request stays on one timeline.
  • Works for every metric, and outliers stay in view.

Costs

  • Probe dots still overlap horizontally: 100 requests in about 170 s.
  • Many readers misread a log axis, so it needs a visible "log scale" label and a mention in the accessible summary.
Option 2

C · Split by phase

recommended

Two small multiples, each with one axis. The audit panel keeps the timeline. The probe panel puts the request number on x, so 100 requests get 100 evenly spaced slots, with its own y-scale and a p25–p75 band.

Gains

  • No overlap by construction: the probe x-axis is fixed at 1–100, so live points fill left to right like the progress bar.
  • Each panel's median uses only its own phase, so the line no longer drops off a cliff.
  • Linear axes that start at zero are honest and easy to read.
  • Two small charts instead of one dual-axis chart follows the dataviz rules.

Costs

  • The panel gets about 140 px taller while a probe runs (the probe panel only shows up once there is probe data).
  • Wall-clock time is gone from the probe panel. The tooltip and the data table still show the start time.
Option 3

D · Focus on the probe

single chart

One timeline, with the y-axis fitted to the probe while one exists (1.3 × its p98). Requests above that are pinned as ▲ markers in an off-scale strip, along with a count. Use "Show all values" to switch back to the full range.

Gains

  • Keeps the familiar single timeline and puts the vertical space where the probe is.
  • Outliers are labelled with a count and stay reachable with hover and the keyboard, so nothing is hidden.

Costs

  • Horizontal crowding stays, and audit values above the fit are flattened onto the strip.
  • The y-range changes when the probe starts, so the jump needs a short, motion-safe transition.
Option 4

E · Log scale with a density treatment

B + lighter marks

B's log axis plus marks that suit dense data. Probe dots are r=3 at 55% opacity with no ring, so overlap reads as darker ink instead of a chain of rings. Behind them is the p25–p75 band and a median per phase.

Gains

  • Clusters read as a shape: the band and line carry the story, and the dots show the spread.
  • The density treatment also applies to C's probe panel.

Costs

  • A single translucent dot is fainter than 3:1. The band, the median line, the tooltip, and the data table carry the values, so they must stay.
  • Still a log axis (see B).

What every variant shares (the accessibility baseline)

  1. Nearest-point hover within 24 px, plus a crosshair. You no longer need to hit an 8 px dot, and it works with touch.
  2. Keyboard: focus a chart, then use ←/→ (PageUp/PageDown for 10, Home/End). A polite live region reads out each request, the same text as the tooltip.
  3. Identity never by colour alone: audit requests are lighter with an outline, failures are a red ×, off-scale requests are ▲, and baseline points are orange, always listed in the legend.
  4. Both themes use the existing v2 tokens. Target teal and baseline orange are the production pair, already validated as ≥ 3:1 against --card in each theme.
  5. Readable ticks: durations from 1,000 ms up are shown as "1.5 s" / "120 s" instead of "120,000" (B–E).
  6. The existing Show data table and the chart's accessible summary stay as they are. C and E add one sentence to the summary: "probe median 1.6 s, p25–p75 1.5–1.8 s".
