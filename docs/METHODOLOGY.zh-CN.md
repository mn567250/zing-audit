# zing — 方法论

> [🇬🇧 English](METHODOLOGY.md) · **🇨🇳 中文** · [🇫🇷 Français](METHODOLOGY.fr.md) · [🇪🇸 Español](METHODOLOGY.es.md) · [🇵🇹 Português](METHODOLOGY.pt.md) · [🇮🇹 Italiano](METHODOLOGY.it.md) · [🇩🇪 Deutsch](METHODOLOGY.de.md)

本文说明 **zing** 如何得出结论：每个检测器发送哪些黑盒探测，探测结果如何换算成分数，
分数如何汇总为维度得分和综合健康分，以及风险结论如何判定。本文描述的是当前实现；
下文每张计分表都是该检测器公开的计分标准（`zing/detectors/*.py` 中的 `SCALE`），
措辞与 Web 界面「**计分标准**」中显示的完全一致。

> zing 给出的是**「行为差异与风险」的黑盒证据，而非欺诈的密码学证明**。
> 请阅读 [局限与负责任使用](#局限与负责任使用)。

## 核心立场

中转站可能出于正当原因出现漂移、更新快照、共享算力池，或对不支持流式的上游做缓冲。
因此 zing 把任何单一信号都视为**风险指标**，而非定论：所有发现都以证据为先、措辞谨慎，
含糊的结果明确保留为**不确定**，而不是强行判为通过或失败。风险结论只有在出现确凿的
高严重度证据时才会升到「高」；而最有力的确认手段始终是**对比模式**（`zing compare`）：
在同一时间用完全相同的探测去打一个**所声称模型的可信基线**。

## zing 如何计分

### 检测器得分

每个检测器都会公开自己的**计分标准**（`DetectorResult.scoring`，由
`zing/detectors/scale.py` 构建）：列出每个检查项所有可能的结果，以及对应的状态、
严重程度和对分数的影响。每条发现都会记录它命中的 `outcome`，因此报告与实际行为
不可能不一致。计分标准采用以下两种方式之一：

- **检查项平均分**（`Scale`，方式 `mean_of_checks`）：每个检查项给出分数，
  检测器得分为计分检查项的平均分。标为**不计分**的结果（通常是无法得出结论的检查项）
  既不抬高也不拉低分数。
- **扣分制**（`DeductionScale`，方式 `deductions`）：得分从 100 开始，发现会扣分
  （`Finding.deduction`）和/或设定上限（`Finding.cap`），取最低上限。

**参数化**检查项把同一组结果行套用到多个对象上（例如响应的每个属性）：每个对象单独计分，
计分标准按检查项只公布一次，报告把各对象列在所属检查项之下。

### 维度得分与状态

zing 对十个维度评分。维度得分为其**各检测器得分的平均值（权重相同）**：检查项多的
检测器不会压过检查项少的，没有数值分数的检测器不计入。维度状态取其检测器得出的最差结论；
但严重程度为「高/严重」的发现会强制判为**失败**，严重程度为「中」的发现会把**通过**
提升为**警告**，与分数无关。每份报告都按维度记录这一过程（`DimensionScore.breakdown`：
每个检测器的得分、是否计入，以及状态调整及其原因发现），并在 Markdown/HTML/PDF 的
**Dimension details** 与 Web 界面「**逐项体检**」的可展开行中展示。检测器自身崩溃时
记为**错误**状态，绝不会中断整个检测。

### 综合健康分、评级与权重

**综合健康分**是所有得出分数的维度的加权平均（见 `zing/scoring.py` 的
`DIMENSION_WEIGHTS`）。未运行的维度（不在该套件中，或在 `custom` 运行中未被选择）
不计入，其余权重重新归一。评级为 A（≥ 90）、B（≥ 80）、C（≥ 70）、D（≥ 60）或 F。

| 维度 | 标识 | 权重 | 作用 |
|---|---|---|---|
| 模型身份 | `model_identity` | 21 | 核心 |
| 上下文窗口 | `context_window` | 19 | 核心 |
| 能力声明 | `capability` | 13 | 核心 |
| 协议兼容 | `protocol` | 8 |  |
| 计费用量 | `billing` | 8 |  |
| 连通性 | `connectivity` | 7 |  |
| 流式真实 | `streaming` | 6 |  |
| 并发可靠 | `reliability` | 6 |  |
| 传输安全 | `security` | 6 |  |
| 性能表现 | `performance` | 6 |  |

三个**核心维度**的失败最直接地指向「货不对板」。

### 风险结论

风险等级由**发现的严重程度**决定，而不是由分数决定。连通性维度的发现不参与判定：
中转站宕机或限流只说明无法评估，并不能证明它换了模型。
**传输类提示**同样不参与（`zing/scoring.py` 中的 `ADVISORY_CHECKS`：`security.tls`、`reliability.success_rate`、`reliability.latency`）：
明文 HTTP、压力下失败或变慢说明的是中转站如何被访问，而不是它提供哪个模型。它们仍会
拉低所在维度的得分和状态，在关键发现中排在替换类发现之后，摘要也会注明它们只是提示（严重程度为中及以上时）。
响应篡改（完整性）和 API 密钥回显仍会抬高风险。

| 风险 | 界面中的名称 | 条件 |
|---|---|---|
| `inconclusive` | 信号不足 | 没有任何核心维度得出可用结果（通过、警告或失败）——例如中转站不可达、模型不在知识库中，或 `custom` 运行未选择任何核心维度 |
| `high` | 货不对板 | 出现「严重」发现；或核心维度中出现「高/严重」发现；或出现两个及以上「高」发现 |
| `medium` | 存在偏离 | 核心维度之外恰有一个「高」发现，或核心维度中出现「中」发现 |
| `low` | 基本可信 | 其他任何「中」发现 |
| `clean` | 一致（疑似真货） | 以上都不满足 |

### 结论置信度

- **低**——所声称的模型不在知识库中，或只与知识库档案模糊匹配（`match_confidence` 为
  `fuzzy`，摘要会注明），或得出可用结果的核心维度少于两个；
- **中**——至少两个核心维度得出了可用结果；
- **高**——使用了基线**且**三个核心维度都得出了可用结果；或置信度为「中」且 LLM
  裁判给出了可用结论。

## 套件、检测器与模式

| 检测器 | 标识 | 维度 | 起始套件 |
|---|---|---|---|
| 连通性与基础补全 | `connectivity` | 连通性 | `smoke` |
| OpenAI 兼容性规范 | `protocol` | 协议兼容 | `standard` |
| 请求属性支持 | `protocol_request` | 协议兼容 | `standard` |
| 响应属性完整性 | `protocol_response` | 协议兼容 | `standard` |
| 确定性与缓存正确性 | `determinism` | 协议兼容 | `deep` |
| 真实上下文窗口与截断 | `context_window` | 上下文窗口 | `deep` |
| 模型身份与降级指纹 | `model_identity` | 模型身份 | `standard` |
| LLM 评委质量 / 降级评估 | `quality_judge` | 模型身份 | `deep`（仅在加 `--judge` 时） |
| 能力声明核验 | `capability` | 能力声明 | `standard` |
| 多模态（视觉）能力核验 | `vision` | 能力声明 | `deep` |
| 流式真实性 | `streaming` | 流式真实 | `standard` |
| Token 计费用量审计 | `billing` | 计费用量 | `standard` |
| 并发可靠性与延迟 | `reliability` | 并发可靠 | `standard` |
| 传输与密钥处理信号 | `security` | 传输安全 | `smoke` |
| 注入系统提示词检测 | `injected_prompt` | 传输安全 | `deep` |
| 响应完整性 / 篡改 | `integrity` | 传输安全 | `deep` |
| 提示前缀缓存（时序） | `prompt_cache` | 传输安全 | `deep` |
| 性能探测 | `performance` | 性能表现 | `deep`（`standard` 下仅在对照基线时运行，5 个请求） |

- **smoke** 运行连通性与安全检测；**standard** 增加协议、身份、能力、流式、计费与
  可靠性检测器；**deep** 增加长上下文、确定性、视觉、注入提示词、完整性、提示词缓存
  与性能探测（加 `--judge` 时还有裁判）；**full** 运行与 deep 相同的检测器，并同时
  测量流式与非流式性能；**custom** 按 deep 深度运行所选维度的全部检测器。
- **纯代码（默认）**：除 `quality_judge` 外，所有检测器都用确定性代码判定——
  文本与正则检查、算术、时序统计。无需第二个模型。
- **代码 + LLM 融合（`--judge`）**：`quality_judge` 询问一个单独配置的可信裁判模型
  （绝不用被测目标本身），目标的回答是否像所声称的模型。未指定 `--judge-base-url` 时，
  对比模式用基线充当裁判。
- **对比模式**（`zing compare`）为探测提供可信基线：`model_identity` 把基线的自我
  身份识别与目标的并列记录，`protocol_request` 把被拒绝的参数再发给基线，
  `integrity` 把基线没有出现的替换升级为「严重」，`quality_judge` 让裁判同时看到
  两侧回答，`performance` 交替探测两个端点。只有使用基线，置信度才能达到「高」。
- **知识库**：所声称模型的画像（`zing/knowledge/data/*.yaml` 以及你在 `kb.db`
  中的自有条目）提供声称的上下文窗口、最大输出、分词器、能力标记、身份关键词和
  行为指纹，探测结果据此判定。每份报告都会记录所用的画像（`knowledge`）。
  所声称的 ID 依次按精确 ID、别名或规范化名称匹配画像，否则进行模糊匹配：取其中
  包含的最长画像名称（`gpt-4o-2024-11-20-custom` → `gpt-4o`），除非 ID 的其余部分
  指向另一个档位或变体（`gpt-5-mini` 不是 `gpt-5`）；若 ID 是截断形式，则只有恰好
  一个模型的名称以它开头时才匹配。因此通用或有歧义的 ID（`gpt-4`、`claude`、
  `gemini-2.5`）不会匹配任何画像，而不是被猜成某个往往更便宜的档位。供应商级
  指纹适用于该供应商的所有模型；只适合部分模型的指纹（知识截止日期、规模档位）
  只列在这些模型上。
- **提示词语言**：所有探测文本都在 `zing/prompts/en.json` 中，无论界面语言如何均为
  英文；只有语言本身就是测量对象的指纹才声明 `prompt_lang` 与 `language_bound`。
  每份报告都会列出实际使用的探测语言（`prompt_languages`）。
- **推理模型：** 短探测若在输出上限处结束、答案缺失，或在推理占用至少一半上限后
  被截断（报告了 `reasoning_tokens`），会以 4,096 token 的上限重试一次，
  以免先思考再作答的模型被误判为失败。上限或计时本身就是测量对象的探测（性能、
  提示词缓存、可靠性、注入提示词、最大输出、`max_tokens` 请求属性）从不重试。
  一旦确知端点会推理（其档案标注 `reasoning: true`，或在首次此类重试之后），
  短探测会从一开始就以 4,096 token 的上限发送，而不再发送两次。
- **请求参数：** 推理模型会拒绝部分参数：在 Chat Completions 上拒绝
  `max_tokens`（改用 `max_completion_tokens`），在所有协议上拒绝 `temperature`
  等采样参数。客户端会省略画像中 `unsupported_params` 所列的参数；若其中列有
  `max_tokens`，则以 `max_completion_tokens` 发送输出上限。没有画像的端点若在
  4xx 中点名了此类参数，该请求会调整后再发送一次，此后的请求一开始就按调整后的方式
  发送；被拒绝的那次尝试不计为中转错误。`protocol_request` 的探测按原样发送，因为
  它评判的正是未经调整的拒绝。

## `connectivity` — 连通性

**能抓到什么.** 不直接命中任何作弊手法——它是其他所有检测器的前置门槛，用来把
「密钥失效 / 配置错误」与「值得审计的中转站」区分开。

**做法.** 访问 `GET /v1/models`（记录所声称模型是否在列表中），并在
`temperature=0` 下发起一次对话补全，要求模型原样回显一个精确的标记串；记录延迟与
回包里的 `model` 字段。

**计分标准**（`zing/detectors/connectivity.py`）：

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `connectivity.models` | 模型列表（/v1/models）有响应。 | 通过 | 100 分 |
|  | 模型列表（/v1/models）无响应；部分中转站会关闭它。 | 警告 · 低 | 60 分 |
| `connectivity.chat` | 对话补全返回了内容，并回显了标记串。 | 通过 | 100 分 |
|  | 对话补全返回了内容，但没有回显标记串。 | 通过 | 85 分 |
|  | 对话补全失败或没有返回内容。 | 失败 · 高 | 0 分 |

检测器状态取其各项检查中最差的一项，因此 `/v1/models` 被关闭时，即使对话正常也是警告。

**注意事项.** `/v1/models` 缺失属正常，许多中转站会关闭它。瞬时网络错误或 5xx
可能导致对话检查失败，应重跑。连通性本身无法证明是**哪个**模型在应答。它的发现
从不抬高风险结论。

## `protocol` — 协议兼容

**能抓到什么.** 中间件破坏接口契约的中转站（丢失对话轮次、忽略停止序列、错误格式
不规范、响应字段缺失或为 0、剥离请求参数），并通过确定性检查识别
`cache.ignore-temperature`。部分覆盖 `capability.json-tool-fakery`。

### `protocol` — OpenAI 兼容性规范

**做法.** 三项探测：一段多轮对话，要求记住前面轮次提到的颜色；一个 `stop` 停止
序列，必须截断输出；以及一个故意无效的请求（空 `messages`），必须以 4xx 拒绝，
最好带 OpenAI 风格的错误体。

Responses API 没有 `stop` 参数，因此对 Responses API 目标不发送 stop 探测，该检查记为不适用（不计分），而不是归咎于中转站。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `protocol.multi_turn` | 记住了之前轮次中的颜色。 | 通过 | 100 分 |
|  | 没有记住之前轮次中的颜色。 | 警告 · 中 | 55 分 |
|  | 没有可用于判断的响应。 | 不确定 · 低 | 不计分 |
| `protocol.stop` | 输出在停止序列处截断。 | 通过 | 100 分 |
|  | 无法从文本确认停止序列的处理。 | 警告 · 低 | 70 分 |
|  | 返回了停止序列之后的文本。 | 警告 · 低 | 60 分 |
|  | 没有可用于判断的响应。 | 不确定 · 低 | 不计分 |
|  | Responses API 没有 stop 参数；未检查，不计分。 | 信息 | 不计分 |
| `protocol.error_schema` | 以 4xx 和 OpenAI 风格的错误体拒绝。 | 通过 | 100 分 |
|  | 以 4xx 拒绝，但响应体不是 OpenAI 风格。 | 警告 · 低 | 80 分 |
|  | 没有 HTTP 响应；无法确认客户端错误处理。 | 警告 · 低 | 55 分 |
|  | 其他 HTTP 状态；无法确认客户端错误处理。 | 警告 · 低 | 55 分 |
|  | 无效请求导致服务器错误（5xx）。 | 失败 · 中 | 35 分 |
|  | 无效请求被接受（2xx）。 | 失败 · 中 | 30 分 |

### `protocol_response` — 响应属性完整性

**做法.** 一次普通的非流式调用；按目标的接口协议（OpenAI Chat Completions、
Anthropic Messages 或 OpenAI Responses；目录见 `zing/detectors/wire_attrs.py`）
逐个属性检查原始响应体。核心属性例如 `model`、`choices[0].message.role/content`、
`finish_reason`、`usage.prompt_tokens`、`usage.completion_tokens` 与
`usage.total_tokens`（必须等于前两者之和）；次要属性为 `id`、`object`、
`created`/`created_at`、`choices[0].index` 与 `type`。本应为正数的计数出现 0
（非空回答却 `completion_tokens: 0`）记为「为零」，而不是有效。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `protocol_response.core` (核心响应属性) | 存在且取值有效。 | 通过 | 100 分 |
|  | 存在但为零或为空（例如 completion_tokens: 0）。 | 失败 · 中 | 20 分 |
|  | 存在但类型或取值错误（例如 total 不等于各部分之和）。 | 警告 · 中 | 40 分 |
|  | 响应中缺失。 | 失败 · 中 | 0 分 |
| `protocol_response.minor` (次要响应属性) | 存在且取值有效。 | 通过 | 100 分 |
|  | 存在但为零或为空。 | 警告 · 低 | 50 分 |
|  | 存在但类型或取值错误。 | 警告 · 低 | 70 分 |
|  | 响应中缺失。 | 警告 · 低 | 60 分 |
| `protocol_response.call` (响应属性探测) | 探测请求没有返回可用于判断的响应体。 | 不确定 · 低 | 不计分 |

### `protocol_request` — 请求属性支持

**做法.** 发送该协议的每个请求参数（约 5 次调用）。有可观察效果的参数各用一次调用，
且必须体现效果：遵循 `system`/`instructions`、输出上限导致 `finish_reason: length`、
`n: 2` 返回两个候选、返回 `logprobs`。只需被接受的参数（`temperature`、`top_p`、
`seed`、各类 penalty、`user`、`top_k`、`metadata`）合并为一次调用，只有被拒绝时
才逐个重试。若知识库在 `unsupported_params` 中列出该参数、向推理模型发送采样参数，
或同协议的基线同样拒绝，则 4xx 记为「模型限制」（不计分），而非「被拒绝」。
工具调用与 JSON 模式归 `capability`，`stop` 归 `protocol`，流式用量归 `streaming`。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `protocol_request.param` (请求参数) | 被接受，且响应中可见其效果。 | 通过 | 100 分 |
|  | 被接受（单次响应无法观察其效果）。 | 通过 | 100 分 |
|  | 被接受，但响应中没有其效果。 | 警告 · 低 | 50 分 |
|  | 以 4xx 拒绝（可能是模型本身的限制）。 | 警告 · 低 | 40 分 |
|  | 以 4xx 拒绝，而基线接受该参数。 | 失败 · 中 | 15 分 |
|  | 被拒绝，但模型本身不支持该参数；不计分。 | 信息 | 不计分 |
|  | 服务器错误或无响应；不计分。 | 不确定 · 低 | 不计分 |

### `determinism` — 确定性与缓存正确性

**做法.** 在 `temperature=1.0`（不设 seed）下发送 4 次相同的创作类提示词：真模型
会有变化；所有样本逐字节相同，说明存在忽略采样参数的响应缓存。对推理模型不做此判定，
因为它们会正当地忽略 temperature。在 `temperature=0` 下发送两次相同的事实类问题，
仅供参考。

只有四个采样中至少三个可用（且所有可用采样都相同）时才判定为缓存；可用采样更少时，该检查结果不确定。

|---|---|---|---|
| `determinism.temp1_variability` | temperature=1.0 下的多次采样结果不同，符合真实采样。 | 通过 | 100 分 |

|  | temperature=1.0 下所有可用采样（至少 3 个）逐字节相同，疑似缓存了响应。 | 警告 · 中 | 55 分 |
|  | temperature=1.0 下可用于判断的采样不足 3 个。 | 不确定 · 低 | 不计分 |
| `determinism.temp0_stability` | temperature=0 下回答相同（符合预期）；仅供参考，不计分。 | 信息 | 不计分 |
|  | temperature=0 下回答不同；仅供参考，不计分。 | 信息 | 不计分 |
|  | 没有可用于判断的响应。 | 不确定 · 低 | 不计分 |

**注意事项.** 网关可能附带厂商特有的额外字段；只对缺失或无效的必填字段告警。
Anthropic↔OpenAI 方言转换会正当地重塑部分结构。确认可疑缺陷的方式是重复探测，
并在可能时使用对比模式。

## `context_window` — 上下文窗口

**能抓到什么.** `context.window-truncation`（中转站宣称 128K/200K/1M，却悄悄裁剪
prompt）以及 `context.lost-in-middle-rag`（廉价的 RAG/摘要垫片只转发部分 prompt）。

**做法.** 在 `temperature=0` 下做大海捞针召回：把一个唯一标记埋入非重复的填充文本中，
要求模型原样返回。

- **探测窗口.** 探测最多到 `upper` = 声称窗口，并受 `--max-context-tokens`（默认
  200K）约束。所有结论都以 `upper` 为准，绝不拿上限以上的那部分更大的声称窗口来评判。
- **长度按真实 token 计.** zing 内置的 token 估算对这段填充文本比真实分词器少算约
  12%（o200k）到 15%（cl100k），因此每个提示按估算值“长度 ÷ 1.2”构建（针和问题计入
  在内）：长度为 N 的一级不会超过 N 个真实 token。证据中的长度（`size`、
  `effective_window`、`top_rung`）都是这种真实 token 预算；阶梯每一行另外记录提示构建时
  的估算值（`heuristic_tokens`）。

1. 最多 7 个长度的阶梯：从 **`upper` 的 90% 处的最高一级**逐级减半（没有任何一级达到
   完整窗口，为回答和聊天模板留出空间），直到 1K 的下限（`context_probe_floor_tokens`）；
   小窗口会把下限降到最高一级的四分之一（2K 窗口探测约 460、920 和 1.8K）。每个长度先
   把针放在**开头**探测（深度 0.0）：保留提示末尾问题的截断只能丢掉开头（本地服务端把
   提示截到其上下文长度时保留的是末尾），因此开头召回即一次调用通过。开头未召回时在结尾
   确认（深度 0.95）；若结尾召回，则用新的针再探测一次开头，再次失败即判该长度为
   **前部截断**失败（在结论的证据中注明）。每个长度最多三次调用；阶梯在第一次确认
   失败处停止。
2. 在最后一次召回成功与第一次失败的长度之间做两步二分搜索。
3. 中段遗忘：在 min(32K, 实测窗口) 的长度下，把针分别放在深度 0.1、0.5、0.9。
   若开头和结尾能召回而中间不能，则用新的针再探测一次中间；只有第二次仍失败才记为一条
   发现。
4. 报错信息提到上下文长度的 4xx 视为按长度拒绝；拒绝 `max_tokens`（推理模型）
   会改用 `max_completion_tokens` 重试，绝不当作上限。
5. 探测超时，或收到错误响应（其他被拒参数、HTTP 错误、5xx、空响应或格式错误的响应），
   会结束阶梯，但不算作失败：最后一个成功召回长度以上的窗口记为未验证（不确定，不计分），
   绝不判为截断或 `no_recall`。只有回答中没有针才算未召回。

实测窗口（召回成功的最大长度）与 `upper` 对比：最高一级召回即为一致（若声称窗口超过上限，
则为**已验证到上限**：上限以上的窗口未被测试）；低于最高一级时，按最高一级中未能回忆的
比例扣分——不低于 `upper` 的一半为警告，低于一半为失败。没有声称窗口时，只报告测量结果，
不计分。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `context_window.window` (实际上下文窗口) | 在最高探测档（探测窗口的 90%）仍能回忆：不扣分。 | 通过 | 不扣分 |
|  | 已在探测上限内验证回忆；上限以上的声明窗口未被测试。 | 通过 | 不扣分 |
|  | 在 50–90% 的探测窗口内能回忆；按最高探测档中未能回忆的比例扣分。 | 警告 · 中 | 最多 −50 分 |
|  | 不到探测窗口的一半就无法回忆；按最高探测档中未能回忆的比例扣分。 | 失败 · 高 | 最多 −100 分 |
|  | 连最小的探测长度都没能回忆起针。 | 失败 · 高 | −100 分 |
| `context_window.lost_in_middle` | 开头和结尾都能回忆，但中间两次都不能。 | 警告 · 中 | −15 分 |
| `context_window.rejected_below_claim` | 远小于声明窗口的提示被以过长为由拒绝。 | 失败 · 高 | 不扣分 |
| `context_window.measured` | 没有可对照的声明窗口：只做测量，不计分。 | 信息 | 不扣分 |
| `context_window.no_ladder` | 在下限与上限之间没有可用的探测长度。 | 不确定 · 低 | 不扣分 |
| `context_window.timed_out` | 探测在达到声明窗口之前超时：说明端点较慢，而非截断的证据。 | 不确定 · 低 | 不扣分 |
| `context_window.probe_error` | 在到达最高探测档之前，探测收到了错误响应（参数被拒、HTTP 或服务器错误）：并非截断的证据。 | 不确定 · 低 | 不扣分 |

**注意事项.** 真正的长上下文模型也会在中段丢针，所以只有**边缘**失败才被视为截断。
临界点附近的召回是概率性的，得出结论前应重跑。该探测受 `--max-context-tokens` 约束，
更大的窗口不会被完整测到（调高它可探测更远）。最高一级位于窗口的 90%，且 token 预算偏保守，
因此窗口最后约 10–15% 永远不会被探测。请与可信基线对比，以区分模型固有行为与垫片行为。

## `model_identity` — 模型身份

**能抓到什么.** `downgrade.silent-substitution`（挂高端名、跑更便宜或开源的后端），
以及 `downgrade.reasoning-collapse`、`downgrade.quantized-distilled`、
`downgrade.partial-probabilistic-routing` 在改变行为时留下的信号。

### `model_identity` — 模型身份与降级指纹

**做法.** 三个相互独立的信号：

1. **自我身份识别**（`temperature=0`），按整词匹配画像中的身份关键词（正品品牌）
   以及竞品品牌列表（画像的 `identity_forbidden` 加内置列表）。只有在正品品牌缺席时，
   竞品品牌才算数；「我是 Claude，不是 GPT」属于良性对比。
   正品品牌是画像的 `identity_keywords` 加上画像自身的名称：厂商键、厂商显示名称开头的名字、
   模型 id 与系列名的首个单词，以及内置列表中同一厂商的其他名称（`z.ai` 也涵盖 `zhipu`）。
   因此模型说出自家厂商永远不算竞品品牌，即使 `identity_keywords` 为空。推导出的名称绝不会
   覆盖 `identity_forbidden`，通用词（「ai」「platform」等）从不计入，平台自己的品牌也不算作
   它所提供的其他厂商模型的品牌。
   同时也是日常英文单词的品牌词（`step`, `command`, `seed`, `spark`, `meta`, `yi`, `grok`）只在这条自我身份识别回答中计入，
   而且只有写成名称时才算（“Meta”“Command R”“grok-2”；位于句首或列表项开头时须带版本号，如“Step-2”）；
   指纹回答中一律不计，因此“let me think step by step”不算竞品品牌。
   拥有这类词的厂商仍把它当作自家品牌。
2. **行为指纹**，来自知识库（知识截止、分词器特征、格式习惯、与语言绑定的探测等）：
   最多 6 个纯代码探测，用 `expect_contains`、`expect_contains_any`、
   `expect_not_contains` 或 `expect_regex` 判定；输出上限 512 token。
   需要更多输出的探测（例如最大输出检查）会被跳过、记为「信息」，由其他探测补位。偏离的指纹按其
   权重占比从 100 分中扣分（每个最多 25 分）；单个偏离只算「低」，两个及以上会追加
   一条「中」的汇总发现。
3. **回包 `model` 字段**（一次普通调用）：容忍快照后缀与别名；出现更低档位的词
   （`mini`、`flash`、`lite`、`8b` 等）或不同模型家族则告警。

知识库中没有画像时，该检测器结果为不确定。
当自我身份识别和所有指纹都没有可用回答、且回显的 `model` 字段没有偏离时，
该检测器同样为不确定且不计分（`model_identity.no_evidence`）：拒绝或清空每个请求的
中转不提供任何身份证据，仅回显所请求的名称本身证明不了什么。部分证据照常计分。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `model_identity.self_id` | 自我介绍提到了正品品牌。 | 通过 | 不扣分 |
|  | 自我介绍提到了竞品品牌，却没有提到正品品牌。 | 失败 · 高 | 上限 20 |
|  | 自我介绍同时提到了正品品牌和竞品品牌（通常只是善意对比）。 | 警告 · 低 | 不扣分 |
|  | 自我介绍既没有提到正品品牌，也没有提到竞品品牌。 | 警告 · 低 | 不扣分 |
|  | 没有可用于判断的响应。 | 不确定 | 不扣分 |
| `model_identity.fp` (行为指纹) | 回答与所声称模型的原生行为一致。 | 通过 | 不扣分 |
|  | 回答偏离了原生行为：按该探针在 100 分中的权重占比扣分。 | 警告 · 低 | 最多 −25 分 |
|  | 回答提到了竞品品牌，却没有提到正品品牌：按该探针的权重占比扣分。 | 失败 · 高 | 最多 −25 分 · 上限 20 |

### `quality_judge` — LLM 评委质量 / 降级评估

**做法.** 仅在加 `--judge` 时运行（deep 及以上）。一小组能区分档位的提示词（多步推理、
精确的编码任务、细致的指令遵循）发给目标，对比模式下也发给基线；一个独立的可信裁判
只看回答，给出结论和置信度。裁判拿到的是所声称的模型（设置了 `claimed_model` 时用它，否则用请求的模型 ID）。
只有裁判明确给出**「高」**置信度、且一个可用的基线佐证了差异（即对目标答出的每个探针
都返回了非空回答）时，裁判结论才会是「高」。置信度为低、中、缺失或无法识别时一律
保持「中」；基线报错或有探针未作答时同样保持「中」。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `quality_judge.verdict` (LLM 评审结论) | 评审模型认为回答与所声称的模型一致。 | 通过 | 95 分 |
|  | 评审模型认为回答不像所声称的模型（置信度为低、中或未给出）。 | 警告 · 中 | 50 分 |
|  | 评审模型确信回答不像所声称的模型（无可用基线）。 | 警告 · 中 | 25 分 |
|  | 评审模型很确定，且可信基线印证了这一差异。 | 失败 · 高 | 25 分 |
|  | 评审模型无法给出结论。 | 不确定 · 低 | 不计分 |
|  | 没有可供评审的目标回答。 | 不确定 · 低 | 不计分 |

**注意事项.** 官方 API 会悄悄更新快照，偏离可能是良性漂移——zing 只报「偏离」，
绝不报「已证实替换」。模型会幻觉出自己的名字，所以自我身份识别绝不单独定论。
中转站可能记住固定的探测集。要得到高置信度结论，必须用对比模式对照与所声称快照
完全一致的基线。

**尚未实现.** 基于嵌入距离的指纹（LLMmap 风格）、分布层面的双样本检验，以及针对
概率路由的大批量采样，都是研究方向，并非当前的检查项。

## `streaming` — 流式真实

**能抓到什么.** `stream.fake-streaming`：中转站把上游整段回答缓冲下来，再以一个或
少数几个分片下发，失去了延迟优势。

**做法.** 一次流式请求（`max_tokens` 256，`stream_options.include_usage`），记录
每个分片的到达时间。三个缓冲信号：**分片过少**（两个及以下）与**首 token 过晚**（TTFT 超过总时长的 90%），
这两项只有收到至少 220 个字符后才判定；以及**间隔均匀**（四个及以上分片、间隔几乎相同，
CV < 0.1，且小于 2 ms：一次性倾倒）。流中没有用量分片则单独告警。

TTFT 指第一个可见内容 token。推理模型（知识库标注为推理模型，或 usage 中报告了推理 token）会先思考再回答，因此它的首 token 较晚只作记录，不计为缓冲；分片过少和间隔均匀两个信号照常计入。流式请求成功但没有返回任何内容时，结果不确定，不计分。
如果模型以流式输出推理过程（推理增量、thinking 块、Responses API 的推理事件），则改为计时任一类型的第一个 token：真正的流式输出很早就开始推理，因此推理和回答都在最后才到达的流即使对推理模型也算作缓冲。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `streaming.healthy` | 分片多、首 token 早、间隔分散：真实的流式输出。 | 通过 | 不扣分 |
| `streaming.few_chunks` | 缓冲信号：第一个扣 40 分，第二个再扣 20 分，之后不再扣分。 | 警告 · 中 | 最多 −40 分 |
| `streaming.late_ttft` | 缓冲信号：第一个扣 40 分，第二个再扣 20 分，之后不再扣分。 | 警告 · 中 | 最多 −40 分 |
| `streaming.reasoning_ttft` | 推理模型的首 token 较晚（它在回答前先思考）：仅供参考，不计为缓冲。 | 信息 | 不扣分 |
| `streaming.uniform_gaps` | 缓冲信号：第一个扣 40 分，第二个再扣 20 分，之后不再扣分。 | 警告 · 中 | 最多 −40 分 |
| `streaming.no_usage` | 流中没有用量分片：仅在没有缓冲信号时扣 15 分。 | 警告 · 低 | 最多 −15 分 |
| `streaming.no_content` | 流式请求成功，但没有返回可供判断的内容；不计分。 | 不确定 · 低 | 不计分 |
| `streaming.failed` | 流式请求失败。 | 失败 · 高 | 上限 0 |

即：真流式 100 · 缺少用量 85 · 一个缓冲信号 60 · 两个及以上 40 · 失败 0 · 无内容：不计分。

**注意事项.** 短输出、快速的小模型或网络抖动都可能看起来像突发下发。上游本就不支持
流式时，中转站只能正当地缓冲——应理解为「该中转站不提供流式」，而非恶意。请重跑，
并与确实支持流式的基线对比。

## `billing` — 计费用量

**能抓到什么.** `billing.usage-inflation`（虚报 prompt 或 completion token）、
`billing.missing-usage`（`usage` 缺失、不完整或自相矛盾），并佐证
`prompt.injected-system-prompt`。

**做法.** 一次确定性调用（总结一段已知文字，`temperature=0`）。对所有模型系列，都用
对语言敏感的启发式方法（约 ±25%）独立计算 prompt 与可见回答的 token 数：zing 不使用任何
分词器库，也不下载分词器。上报的 prompt token 超过估算的 2.5 倍且多出 50 个以上，视为虚高。
推理模型的 completion token 正当地包含隐藏的推理 token，不告警；否则 completion token
超过估算的 3 倍且多出 80 个以上时给出较轻的警告，绝不判为失败，因为对简短回答的估算噪声较大。
`total` 必须等于 `prompt + completion`（误差 ±2），只有总数而没有拆分也会告警。
少报（低于估算的一半）仅供参考（对买方无害）。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `billing.request-failed` | 没有可用于判断的响应。 | 不确定 · 低 | 不扣分 |
| `billing.missing-usage` | 响应完全没有返回 token 用量。 | 警告 · 中 | 上限 75 |
| `billing.usage-inflation` | 上报的提示 token 远超独立估算。 | 失败 · 高 | 上限 55 |
| `billing.usage-inflation-completion` | 上报的补全 token 远高于启发式估算。 | 警告 · 中 | 上限 70 |
| `billing.reasoning-tokens` | 补全 token 多于可见文本，这对推理模型来说属于正常。 | 信息 | 不扣分 |
| `billing.usage-undercount-prompt` | 上报的提示 token 远低于估算（不损害买方）。 | 信息 | 不扣分 |
| `billing.usage-undercount-completion` | 上报的补全 token 远低于估算（不损害买方）。 | 信息 | 不扣分 |
| `billing.total-mismatch` | 上报的总数不等于提示 token 与补全 token 之和。 | 警告 · 低 | 上限 90 |
| `billing.partial-usage` | 用量只给出总数，没有提示/补全的拆分。 | 警告 · 中 | 上限 80 |
| `billing.usage-consistent` | 上报的用量在独立估算的容差范围内。 | 通过 | 不扣分 |

探测请求失败时，该检测器不计分。

**注意事项.** chat 模板和特殊 token 会带来一个小的固定偏移，因此不应期望精确相等。
若实际服务的模型与所声称的不同，「正确」的分词器也就未知。隐藏的推理 token 无法从
外部计数。一次探测只测一个长度；要发现随长度增长的倍数，需要多次运行或对比模式。

## `reliability` — 并发可靠

**能抓到什么.** `throttle.rate-limit-quality` 的一部分：在适度并发下失败或变得极慢
的中转站。

**做法.** 以受限并发（`--concurrency`，默认 3）发送一批相同的小请求
（`--reliability-requests`，默认 8）。成功率只按真正尝试的请求计算：HTTP 429 是
正当限流，单独计列。得分扣除失败占比；p95 延迟超过 30 秒时，保留剩余分数的 85%。仅 1 个请求失败（即默认 8 个
中出现一次瞬时 5xx），或不超过较大批次的 10%，只要成功率不低于 80% 就是警告；更多则为失败。
检测器状态取其各项发现中最差的一项。这些发现属于传输类提示，永远不会抬高风险结论。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `reliability.success_rate` | 突发中的所有尝试请求都成功了。 | 通过 | 不扣分 |
|  | 仅 1 个请求或不超过 10% 的尝试请求失败（成功率不低于 80%）；按失败比例扣分。 | 警告 · 低 | 最多 −20 分 |
|  | 失败的请求多于上述范围；按失败比例扣分。 | 失败 · 中 | 最多 −100 分 |
|  | 所有请求都被限流（HTTP 429）：不计分。 | 不确定 · 低 | 不扣分 |
| `reliability.latency` | 负载下 p95 延迟超过 30 秒；扣除剩余分数的 15%。 | 警告 · 低 | 最多 −15 分 |
| `reliability.rate_limited` | 部分请求被限流：属于正常限流，不计入。 | 信息 | 不扣分 |
| `reliability.skipped` | 可靠性探测已关闭。 | 信息 | 不扣分 |

专门的速度测量属于 `performance` 维度。

**注意事项.** 真正的厂商在真实负载下也会变慢、也会返回 429。单次快照看不到与时段
相关的行为；`zing watch` 可按计划反复检测。

**尚未实现.** 跨时段、按负载条件的质量探测，以及共享上游密钥的信号
（`infra.shared-upstream-key`：空闲时配额仍在减少、泄漏的上游 request id）
都在路线图上。

## `security` — 传输安全

**能抓到什么.** `prompt.injected-system-prompt`、`integrity.response-tampering`、
指向 `privacy.prompt-logging-leakage` 的证据（前缀缓存），以及基本的传输与密钥卫生。

### `security` — 传输与密钥处理信号

**做法.** 检查端点是否使用 HTTPS、API 密钥是否从未原样出现在响应中，以及哪些响应头
暴露了上游或代理（`server`、`via`、`x-powered-by`、`x-upstream-*`、`x-litellm-*` 等；
仅供参考）。它也会说明边界：提示词是否被记录、上游密钥是否共享，都无法从外部证明。通过明文 HTTP 访问本机或内网
（`localhost`、`127.x`、`192.168.x`、`*.local` 等——自托管模型）只是警告且不设上限，
因为密钥不会经过公网；访问其他任何主机的明文 HTTP 仍为失败 · 高。无论哪种情况，
`security.tls` 都是传输类提示，永远不会抬高风险结论。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `security.tls` | 接口使用 HTTPS。 | 通过 | 不扣分 |
|  | 接口不是 HTTPS；API 密钥以明文传输。 | 失败 · 高 | 上限 40 |
|  | 通过明文 HTTP 访问本机或内网主机；API 密钥不会经过公网。 | 警告 · 低 | 不扣分 |
| `security.key_echo` | API 密钥没有出现在响应中。 | 通过 | 不扣分 |
|  | API 密钥原样出现在响应中。 | 失败 · 高 | 上限 30 |
| `security.headers` | 没有响应头暴露上游（仅供参考）。 | 通过 | 不扣分 |
|  | 响应头暴露了上游或代理（仅供参考）。 | 信息 · 低 | 不扣分 |
|  | 没有可检查的响应头。 | 不确定 | 不扣分 |
| `security.note` | 提示日志与共享上游密钥无法从外部证明。 | 信息 | 不扣分 |

### `injected_prompt` — 注入系统提示词检测

**做法.** 两个相互独立的迹象。(1) **固定的输入 token 开销**：不带系统消息，发送两条
长度不同的用户消息；上报的 `prompt_tokens` 减去独立估算应当很小。至少 30 token 的
开销、且在两个长度下保持不变（相差不超过 16），说明被悄悄前置了隐藏提示词，而不是
按比例虚报。(2) **泄漏探测**：要求模型复述此前的所有指令。只有两者同时出现才达到「中」。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `injected_prompt.verdict` (注入的系统提示) | 输入 token 开销很小，且没有泄露隐藏指令。 | 通过 | 100 分 |
|  | 被要求时泄露了类似指令的文本（单独来看较弱）。 | 信息 · 低 | 85 分 |
|  | 存在较大的固定输入 token 开销，且不随消息长度变化。 | 警告 · 低 | 75 分 |
|  | 固定的输入 token 开销与泄露的前置提示同时出现。 | 警告 · 中 | 55 分 |
|  | 没有可用的提示 token 数来测量开销。 | 不确定 | 不计分 |

### `integrity` — 响应完整性 / 篡改

**做法.** 一组已知答案的标记值，其取值很敏感——一个安装 URL 和一个锁定版本的
`pip install` 包——必须原样返回。精确回显即通过；没有回显（改写、拒答）为不确定；
只有结构保留而**取值被替换**才算篡改。对比模式下，可信基线没有出现的替换记为「严重」。
只有原样返回标记值的基线才算佐证：基线报错或没有返回可用内容时什么也证明不了，
替换仍记为「中」（证据字段 `baseline_unavailable`）。
在输出上限处被截断的回答记为不确定，而不是替换。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `integrity.verdict` (响应完整性) | 已知答案的标记值原样返回。 | 通过 | 100 分 |
|  | 某个标记值被替换（尚未经基线确认）。 | 失败 · 中 | 45 分 |
|  | 某个标记值被替换，而可信基线保持原样。 | 失败 · 严重 | 10 分 |
|  | 没有标记值被原样回显，无法评估篡改。 | 不确定 | 不计分 |

### `prompt_cache` — 提示前缀缓存（时序）

**做法.** 把一段约 1200 token 的唯一前缀流式发送两次（冷启动，再热启动），再把另一段
对照前缀发送一次。若热启动的 TTFT 低于冷启动和对照组各自 TTFT 的一半，且比冷启动
至少快 150 ms，则说明前缀缓存已启用。始终仅供参考：前缀缓存是正当的优化。

| 检查项 | 结果 | 状态 | 计分 |
|---|---|---|---|
| `prompt_cache.verdict` (提示前缀缓存) | 重复的提示前缀返回明显更快：前缀缓存已启用。 | 信息 | 不计分 |
|  | 重复的提示前缀没有明显更快。 | 信息 | 不计分 |
|  | 一个或多个计时探测没有返回可用的时间。 | 不确定 | 不计分 |

**注意事项.** 被要求泄漏时，模型会编造假的「系统提示词」，所以单独的泄漏只算「低」。
方言转换会重塑工具调用 JSON；只有**取值**被替换才算数。条件式篡改（只针对特定关键词、
特定客户端或在预热之后）可以躲过有限的探测。黑盒下**无法证明**是否记录日志，zing
也无法用单个密钥证明**跨用户**共享缓存：没有时序信号并不能证明 prompt 没被记录。

## `performance` — 性能表现

**测什么.** 端点有多**稳定**，而不是有多快。慢但稳定的本地或自托管模型同样得高分；
绝对速度只与参考值对比。

**做法.** 专用探测在 deep、full、custom 下运行；standard 下仅在对比模式运行（每侧
5 个请求，不足以做稳定性检查）。每个端点：三次 `GET /models` ping、一次预热请求
（报告为冷启动）、`--performance-requests` 个统一请求（默认 100 个），每个输出
`--performance-max-tokens` 个 token（默认 128），deep/full 下再按 `--concurrency`
做一次突发并发。每个请求都不可缓存：提示词以随机请求 id 开头、主题轮换、不发送任何
缓存或推理参数；仍从缓存返回的响应会被标记并排除在统计之外。探测默认使用流式
（不支持流式的中转站用 `--performance-non-streaming`）；full 交替测量两种模式。
对比模式下目标与基线交替发请求，使网络波动对两侧影响相同。
只有缓存的输入 token 覆盖至少一半提示词时才计为缓存命中：本地服务（Ollama、
llama.cpp、LM Studio）会复用每个提示词的聊天模板缓存，这并不是存储的回答。
检测中的每次调用都会保存为一条请求记录（`performance.requests`，只有数字，从不含提示词或
回答文本）；其 `start_ms` 从报告的 `started_at`（UTC）算起，因此可以还原每次调用的时间。

稳定性采用尾部比（延迟与 TTFT 为 p90 ÷ p50，吞吐为 p50 ÷ p10），单个离群请求不会像
影响标准差那样影响它；至少需要 10 个有效样本。参考值为可信基线；没有基线时，用知识库
画像中的 `performance.decode_tps` 区间。

## 嵌入接口（embedding surface）

审计的 **surface**（默认 `chat`，或 `embedding`）决定使用哪些检测器；测试套件仍决定深度。嵌入审计只发送
`POST /embeddings` 请求，复用对话的维度以及共用的 0–100 分和 A–F 等级，权重按 surface 区分。维度不匹配
（模型身份，「高」）会使风险为「高」，就像对话中模型被替换一样。

| 检查 | 标识 | 维度 | 检测内容 |
|---|---|---|---|
| 连通性 | `embed.connectivity` | 连通性 | 端点返回格式正确的向量 |
| 向量维度 | `embed.dimension` | 模型身份 | 返回的长度 vs 声称模型的原生维度（知识库，或 `claimed_dimensions`） |
| 回包模型 | `embed.model_field` | 模型身份 | 响应的 `model` 字段是否为声称的模型 |
| 向量漂移 | `embed.drift` | 模型身份 | 固定探测输入的向量 vs 上一次已保存的运行 |
| 确定性 | `embed.determinism` | 并发可靠 | 同一输入两次得到余弦 ≥ 0.9999 |
| 区分度 | `embed.distinctness` | 能力声明 | 无关输入的余弦低于 0.98 |
| 性能探测 | `performance.embed` | 性能表现 | 延迟、冷启动、吞吐量、批量扩展 |

**向量漂移。** 每次运行保存一个固定输入的单位向量的前 64 个分量。同一目标、同一声称模型的下一次运行
（`zing embed`、在 Web 界面检测页面通过接口类型选择器启动的嵌入检测，或嵌入监控）把它的向量与该样本比较：余弦 **≥ 0.995** 为稳定（PASS），
**0.95 到 0.995** 为有偏移（WARN，「中」：重新部署或量化），低于 **0.95** 或长度不同说明模型被替换
（FAIL，「高」）。第一次运行没有可比较的对象，只记录基线（INFO）。

**性能探测。** 与对话探测的启用条件相同：在 deep、full 和 custom 下运行，standard 下仅在有基线时运行。
先 ping 一次并发送一个预热请求（冷启动），然后发送统一的单输入请求、16 个输入的批量请求，deep/full 下
还有一次并发突发。每个输入都带随机 nonce；不同输入得到完全相同的向量会被标记为缓存并排除在统计之外。
它报告延迟 p50/p95、冷启动、输入/秒和输入 token/秒、延迟与吞吐量的稳定性、错误以及负载下的稳定性。
**批量扩展**比较批量请求中每个输入的延迟与单个请求的延迟：达到 0.6x 及以上说明批量被拆分或串行处理
（线性，WARN「低」）。知识库中没有速度参照；原始速度只在对照基线时计分。

## 重排接口（rerank surface）

重排审计（`surface` 为 `rerank`）只发送 `POST /rerank` 请求，在共用的 0–100 分和 A–F 等级上以自己的
权重评分：模型身份 30、能力声明 30、性能表现 20、并发可靠 10、连通性 10。已知答案的排序失败（能力声明，
「高」）或模型被替换（模型身份，「高」）会使风险为「高」。

| 检查 | 标识 | 维度 | 检测内容 |
|---|---|---|---|
| 连通性 | `rerank.connectivity` | 连通性 | 端点返回格式正确的排序 |
| 已知答案 | `rerank.known_answer` | 能力声明 | 含一个明显相关文档的探测把它排在第一 |
| 回包模型 | `rerank.identity` | 模型身份 | 响应的 `model` 字段是否为声称的模型 |
| 排序漂移 | `rerank.drift` | 模型身份 | 固定探测的排序和分数 vs 上一次已保存的运行 |
| 确定性 | `rerank.determinism` | 并发可靠 | 同一查询两次得到相同的排序和分数 |
| 性能探测 | `performance.rerank` | 性能表现 | 延迟、冷启动、文档/秒、随文档数量的扩展 |

**排序漂移。** 每次运行保存一个相关度分级的固定探测的排序和取整后的分数。同一目标、同一声称模型的下一次
运行与之比较：排序相同且分数变化在 **0.01** 以内（取最大的分数变化；仅当分数大于 1 时按相对值计算）为稳定（PASS），**0.01 到 0.1** 为有偏移（WARN，「中」），
排序不同或变化超过 **0.1** 说明模型被替换（FAIL，「高」）。第一次运行只记录基线（INFO）；探测本身改变时
绝不会被当作漂移。

**性能探测。** 与对话探测的启用条件相同（deep、full 和 custom；standard 下仅在有基线时）。每一轮发送
一个针对 **4 个文档**的唯一查询和一个针对 **32 个文档**的查询；deep/full 下随后还有一次并发突发。细粒度
分数与另一查询重复的响应会被标记为缓存并排除在统计之外；有文档未被打分的响应算作失败请求。它报告延迟 p50/p95、冷启动、文档/秒和输入
token/秒、稳定性、错误以及负载下的稳定性。**随文档数量的扩展**：如果 32 个文档的请求每个文档的开销达到
4 个文档请求的 0.6x 及以上，说明中转站在拆分或串行处理文档（线性，WARN「低」）。知识库中没有速度参照；
原始速度只在对照基线时计分。

## 局限与负责任使用

**zing 报告的是偏离与风险，而非欺诈的证据。** 结论使用谨慎措辞（clean / low /
medium / high / inconclusive），含糊结果保留为不确定，只有在确凿的高严重度证据下
才升为「高」。

**黑盒审计本质上无法证明的事：**

- **是否记录 prompt 或留存数据。** 时序信号能证明存在缓存；没有信号**不代表**
  prompt 未被记录。
- **响应完整性**：没有厂商签名的响应时，条件式篡改可以躲过有限的探测。
- **密钥共享或被盗**：最多只能标记共享池**风险**。
- **良性漂移还是替换**：官方 API 会悄悄更新快照。
- **是否始终路由到同一模型**：中转可能做概率性路由，一次检测只能看到它发出的请求。

**方法.** 依赖精确比对的发现使用 `temperature=0` 与受限的提示词。每条发现都附带证据
（输入、观测值、计数、耗时），每份报告都记录所用的画像、提示词语言与设置，使结果可以
被独立复核。中转站可能感知测试：请在不同时间重跑，并优先用对比模式对照**与所声称
快照完全一致**的可信基线——这是区分模型行为与中转行为最有力的手段，也是达到高置信度
的唯一途径。

**负责任披露.** **切勿**仅凭一份 zing 报告就公开指控厂商。行动前请：加大样本量、
在不同时间重跑、用对比模式确认，并排除漂移、网络与负载等解释。若严重疑虑仍在，请先
私下向厂商反馈——以「对观察到的行为提出疑问」而不是「指控」的方式。
